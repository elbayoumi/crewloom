# Concurrent development example

This guide is the operator's reference for the runnable example in
[examples/concurrent-development](../examples/concurrent-development/README.md). It shows one
complete concurrent development batch: three tasks in a dependency graph, each task's code
generated by a real `model` step inside its own Git worktree, each generated file verified by
a real container command, one combined acceptance over the integrated tree, and one
credential-reviewed decision that moves the checked-out tree by a single fast-forward.

The coordinator itself, its manifest contract and its evidence model are documented in
[COORDINATOR.md](COORDINATOR.md); execution and failure handling are in
[EXECUTION.md](EXECUTION.md); credential-verified review is in
[ENFORCEMENT.md](ENFORCEMENT.md). Read those first if you are changing anything here.

## Requirements

Python 3.9+, Git, a working Docker daemon, and a locally available `python:3.14-slim` image:

```bash
docker pull python:3.14-slim
```

One provider credential in the environment for the host you choose. There is no provider call
anywhere in the example's own scripts.

## The application

`ledgerline` builds one report from a JSON document: an invoice summary and an execution plan,
in one language, English or Arabic. The command is the user interface.

```
python3 src/app.py --data data/ledger_en.json --out artifacts/report.json
python3 src/app.py --data data/ledger_ar.json --out artifacts/report-ar.json --language ar
```

The generated modules are `src/billing.py` (invoice arithmetic), `src/planning.py` (dependency
depth, priority and capacity waves), `src/report.py` (the combined document) and `src/app.py`
(the command). Two helpers are reused rather than regenerated: `src/money.py` and
`src/scheduling_support.py` are copied verbatim from the
[context-study example](../examples/context-study/README.md) and covered by frozen fixture
tests in `tests/`.

Two application decisions are worth naming, because the acceptance commands assert them
numerically rather than by marker string:

- **One rounding decision per currency group.** Per-line taxes are accumulated unrounded and
  quantized once per group. For the frozen Arabic sample the group tax is `45.01` while the
  per-line-rounded total is `45.00`; the report carries both numbers.
- **A refund is a negative line, not a signed quantity.** The `refund` category negates an
  otherwise positive line, so a negative amount without that category is refused.

## The task graph

| Task | Declares | Generation step | Command acceptance |
| --- | --- | --- | --- |
| `billing` | — | `src/billing.py` from `contracts/invoicing.md` | `tools/check_billing.py`, 21 cases |
| `planning` | — | `src/planning.py` from `contracts/planning.md` | `tools/check_planning.py`, 20 cases |
| `report` | `billing`, `planning` | `src/report.py`, `src/app.py` from `contracts/report.md` with both ancestor modules as declared inputs | `tools/check_report.py`, 14 cases |
| integration | every task output | — | `tools/check_combined.py`, 13 cases, and `tools/run_helper_tests.py` over `tests/` |

The dependent task's generation step declares `src/billing.py` and `src/planning.py` as inputs,
which is how the merged ancestors reach its prompt. Its acceptance also reads the ancestors'
acceptance artifacts and checks that the source digest they recorded is the digest of the
module bytes now on disk.

## Commands

`--project` and `--project-id` are explicit everywhere; `--manifest` is relative to the project.

### Setup

```bash
python3 examples/concurrent-development/setup_project.py \
  --destination /private/tmp/ledgerline \
  --project-id ledgerline-demo \
  --model-host openai \
  --model gpt-4.1
```

Setup performs, in order and with the library's own APIs: a fresh-directory and canonical-path
check, an installed-role and bound-project and Git-work-tree refusal check, an exact-host and
exact-model check with no fallback, template substitution read before the first write, the
portable configuration and local binding through `pb.bootstrap` with no entered-task
reservation, `crewloom.install_skills` for exactly the two roles the workflows name, the frozen
helper tests, one Git commit through the repository's configured hooks with no `--no-verify`
and no hook disabled, `crewloom reviewer register` for a fresh principal with the credential
written to an owner-only file, and finally `task_coordinator.validate` as the acceptance of
the setup itself.

Refusals happen before the first write, and each one names its cause: an existing destination,
a symlinked parent, a destination inside the Crewloom installation, another bound project, an
installed role tree or another Git work tree, a blank model, an unknown host, an installed-CLI
host without its operator decision, that decision for a tool-free host, and a missing provider
credential.

### Validate, run, status

```bash
crewloom coordinator validate --project $PROJECT --project-id $ID --manifest coordinator.json
crewloom coordinator run      --project $PROJECT --project-id $ID --manifest coordinator.json
crewloom coordinator status   --project $PROJECT --project-id $ID --manifest coordinator.json
```

`run` needs `--allow-host-cli` as well when the manifest task declares `native_host_cli`.

### Prepare, review, publish

```bash
crewloom coordinator prepare --project $PROJECT --project-id $ID --manifest coordinator.json
git -C $PROJECT diff $BASE..$CANDIDATE
export CREWLOOM_REVIEWER_TOKEN="$(cat $PROJECT/.crewloom/reviewer-token-example-reviewer)"
crewloom coordinator review  --project $PROJECT --project-id $ID --manifest coordinator.json \
  --expected-base $BASE --candidate-head $CANDIDATE --diff-sha256 $DIFF
crewloom coordinator publish --project $PROJECT --project-id $ID --manifest coordinator.json \
  --expected-base $BASE --candidate-head $CANDIDATE --diff-sha256 $DIFF
```

`$BASE`, `$CANDIDATE` and `$DIFF` come from the `prepare` report. The credential is delivered
through `CREWLOOM_REVIEWER_TOKEN` or `--reviewer-token-stdin`, never as an argument, and only
its hash is stored. Inspect the actual diff and digests before authorizing: setup approves
nothing, and no report approves generated output.

### Cancel

```bash
crewloom coordinator cancel --project $PROJECT --project-id $ID --manifest coordinator.json --reason "operator stop"
```

## Failure, resume and cancellation

| Situation | Recorded behaviour |
| --- | --- |
| A task's command acceptance fails | The task is `failed`, every dependent task is `blocked` with the blocking IDs, `prepare` refuses partial acceptance, and the root does not move. The unaccepted generated file stays in the worktree, uncommitted. |
| A refused native CLI opt-in | The task is `blocked` before any provider call and the recorded evidence is empty. The refused per-run grant is recorded separately from the committed manifest decision. After granting `--allow-host-cli`, retry the same batch ID and project; successful tasks are re-proved and reused. |
| Two identical attempts | The executor refuses a third identical command or generation attempt for unchanged inputs. Change the cause, then use a new batch ID. |
| Interrupted controller | The kernel released the advisory lock, so a second controller is admitted. `run` re-proves every verified task and never generates or executes it twice. |
| Cancellation | A live controller stops dispatching, drains in-flight work, releases the root and keeps verified evidence. A cancelled batch needs a fresh `run`, `prepare` and `review` before publication. |
| Changed manifest, criteria, base or worktree identity | Refused by name before any write. Use a new batch ID. |

## Acceptance evidence

```bash
python3 -m unittest discover -s scripts -p test_development_example.py
CREWLOOM_DOCKER_TESTS=1 python3 -m unittest discover -s scripts -p test_development_example.py
```

Without the variable the real Docker cases are skipped. With it, `scripts/test_development_example.py`
runs this project through the real coordinator, and asserts:

- three distinct worktree checkout identities, overlapping recorded task intervals, and a
  generation request whose prompt really contained both merged ancestor modules;
- per-task evidence with a succeeded generation attempt, the consuming command acceptance, and
  the generated digest equal to the digest that acceptance ran;
- a repository `pre-commit` hook that ran for every task commit, on exactly the tree that
  became it;
- the root `HEAD` and the absence of every generated file before the reviewed decision, and a
  refused `publish` before it;
- a combined acceptance over the integrated tree that produced the expected English and Arabic
  numbers, the mixed-currency and refund case, byte-identical repeated runs, and exit status 2
  with no output for a cycle, an unknown field, a float amount, a boolean quantity and an
  unknown category;
- a credential-required review refusal, a decision delivered over standard input, a published
  candidate equal to the reviewed head, and a refused second publication;
- the generated command actually run in the published root afterwards;
- a failed task quality gate blocking its dependent and publication with the root unchanged;
- an installed-CLI host refused without both decisions, with no provider request recorded, and
  verified end to end when both are given.

Only the generation transport is replaced. A stand-in provider returns the module bytes shipped
in `examples/concurrent-development/fixtures/generated/` and records every request it received;
Docker, the executor, the attempt ledger, the role context, the worktrees, the commit evidence,
the review and the publication are all real. That is evidence about this toolkit's
coordination and verification. It is not evidence about any model's quality, latency or cost,
and no such figure is claimed.

## Limits

- One batch per root, at most four workers, one fixed base, one image. The example uses two
  workers and three tasks.
- A generation is accepted only with a real command acceptance that consumed its bytes. The
  evidence is a digest match against recorded attempts, not a quality verdict.
- A reviewer credential proves possession of a registered principal's secret. It does not prove
  a distinct human reviewed the work, and neither does a declared reviewer label.
- An installed CLI host is a native host exception, not an OS sandbox, and the manifest decision
  plus the run flag are two separate explicit decisions that both default to no.
- Managed coordination does not stop a host tool that writes outside these guards, and claiming
  a lock back does not stop a container that outlived its process.
- The example refuses a destination inside another Git work tree, so it cannot be used to
  develop inside a larger repository without adapting that check.
- No live provider run, no billed-token measurement and no independent human review is part of
  this example or of continuous integration.
## Actual provider pilot

The [2026-10-05 pilot](../examples/evaluation/application-pilot-20261005.json) dispatched two OpenCode `opencode/space-bunny-free` generations with a 300-second limit. Billing generation completed but failed `missing_description_is_refused`; planning timed out. The dependent report stayed blocked, the root did not move, and publication was refused. Both attempts remain recorded without replacements. The 37 passing application tests use a deterministic provider stand-in with actual Docker and credential review; they establish application and orchestration behavior. This provider attempt did not establish generated application quality.

The subsequent documentation correction makes both nonempty description fields explicit in the billing contract. Planning chunks describe an ordered display plan and can contain consecutive depths; the coordinator DAG separately controls real execution dependencies. The original failed pilot used the earlier contract bytes and is retained unchanged.
