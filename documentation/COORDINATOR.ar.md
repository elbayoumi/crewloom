# منسّق المهام المتزامنة — Crewloom

`crewloom coordinator` ينفّذ رسماً بيانياً للمهام داخل مشروعك كدفعة حقيقية: المهام المستقلة
تعمل على نحو متزامن في أشجار عمل Git منفصلة، والمهمة التي تعتمد على غيرها تقرأ فعلاً مخرجات
الأسلاف الملتزَمة، ولا يتغيّر الشجرة المفحوصة إلا بعد قرار مراجعة صريح. هذا يستبدل الإجراء
اليدوي «أنشئ شجرة عمل لكل مهمة ثم ادمجها»، وهو ليس مجدول مهام ولا يولّد شيفرة.

كل مهمة تشغّل المنفّذ المُدار الموجود مسبقاً، `workflow.run`، لذلك يبقى حد العزل، ووسيط
المخرجات المُعلَنة، وسياسة صورة Docker، وسجلّ المحاولات هي نفسها المستخدمة في أي workflow عادي.
اقرأ [التنفيذ ومعالجة الفشل](EXECUTION.md) و[التطبيق المُدار](ENFORCEMENT.md) أولاً.
المرجع الإنجليزي: [COORDINATOR.md](COORDINATOR.md).

## المتطلبات

بايثون 3.9+ على لينكس أو ماك أو WSL، وGit، وDocker عبر daemon يعمل، وصورة تنفيذ متاحة محلياً،
ومشروع مربوط مسبقاً:

```bash
docker pull python:3.14-slim
crewloom project enter --project /path/to/project --project-id my-project --task-id bind-root --role context-guardian
```

يتطلب المشروع المربوط وجود `crewloom.project.json` و`.crewloom/binding.json`. بدون هذا الربط يرفض
المنسّق العمل، ولا يستنتج المشروع أبداً من مجلد العمل الحالي أو من عميل سابق.

## عقد ملف الوصف

`coordinator.json` ملف JSON داخل المشروع، والمسارات نسبية إلى جذر المشروع القانوني.

```json
{"schema_version":1,"id":"feature-batch","project_id":"my-project","base":"HEAD","workers":2,
 "tasks":[{"id":"left","workflow":"workflows/left.json","depends_on":[]},
          {"id":"right","workflow":"workflows/right.json","depends_on":[]},
          {"id":"combine","workflow":"workflows/combine.json","depends_on":["left","right"]}],
 "integration":{"workflow":"workflows/integration.json"}}
```

| الحقل | المعنى |
| --- | --- |
| `schema_version` | القيمة `1` بالضبط. |
| `id` | معرّف ثابت بأسلوب kebab-case؛ يسمّي مجلد الحالة والفرع وحجز وقت التشغيل. |
| `project_id` | هوية المشروع المحمولة؛ يجب أن تطابق `--project-id` والربط المحلي. |
| `base` | الالتزام الدقيق الذي تبدأ منه كل مهمة، ويجب أن يُحلّ في هذا المستودع وأن يكون `HEAD` المفحوص. |
| `workers` | عدد المهام المتزامنة، من 1 إلى 4، والافتراضي 2. |
| `language` | اختياري: `en` أو `ar`، والافتراضي `en`. |
| `tasks` | من 1 إلى 32 مهمة؛ لكل واحدة `id` و`workflow` و`depends_on` اختياري. |
| `integration` | الـ workflow الذي يقبل النتيجة المدمجة. |

يشير `workflow` إلى [خطة workflow عادية](EXECUTION.md#plan-contract) داخل المشروع. تُرفض الحقول
غير المعروفة ومعرّفات المهام المكررة والمفاتيح غير المعروفة والدورات الاعتمادية على النفس
والاعتماديات المفقودة ومعرّف workflow مشترك وخطوات `task` اليدوية قبل إنشاء أي شيء.
خطوات `model` مدعومة بشرط أن تستهلك فحوص أوامر لاحقة كل مخرجاتها وتُسجّل أدلة التنفيذ.

يجب أن يعلن workflow الدمج **كل مخرجات المهام كمدخلات معلنة**. هذا ما يجعل قبوله قبولاً للنتائج
المدمجة لا ادعاءً ناجحاً من طرف واحد، ويُفحص ساكناً قبل وجود أي شجرة عمل.

## الأوامر

`--project` و`--project-id` مطلوبان لكل إجراء، و`--manifest` نسبي إلى المشروع. تقرير JSON هو
المرجع المعتمد.

```bash
crewloom coordinator validate --project /path/to/project --project-id my-project --manifest coordinator.json
crewloom coordinator run      --project /path/to/project --project-id my-project --manifest coordinator.json
crewloom coordinator status   --project /path/to/project --project-id my-project --manifest coordinator.json
crewloom coordinator prepare  --project /path/to/project --project-id my-project --manifest coordinator.json
crewloom coordinator review   --project /path/to/project --project-id my-project --manifest coordinator.json \
  --principal reviewer-alex --expected-base <base> --candidate-head <head> --diff-sha256 <digest>
crewloom coordinator publish  --project /path/to/project --project-id my-project --manifest coordinator.json \
  --expected-base <base> --candidate-head <head> --diff-sha256 <digest>
crewloom coordinator cancel   --project /path/to/project --project-id my-project --manifest coordinator.json
```

| الإجراء | ما يفعله |
| --- | --- |
| `validate` | فحص أولي للقراءة فقط: الملف، الهوية، أساس Git، الـ workflows والرسم البياني. لا يكتب شيئاً، ولا يحدّث فهرس Git. |
| `run` | يبدأ الدفعة أو يستأنفها: يربط شجرة عمل كل مهمة ثم ينفّذ المهام الجاهزة بعدد متزامن لا يتجاوز لا يتجاوز `workers`. |
| `status` | يقرأ الدفعة المسجّلة وأشجار العمل ومراجع الأدلة والحدود المسجّلة. |
| `prepare` | ينشئ شجرة عمل الدمج، يدمج كل التزامات المهام المتحقّقة مرة واحدة، ثم يشغّل القبول المدمج الفعلي. |
| `review` | يسجّل قرار مراجعة واحداً على الأساس ورأس المرشح وبصمة الفرق المحددة بالضبط. |
| `publish` | يعيد التحقق من كل شيء ثم يقدّم الجذر تقدّماً سريعاً واحداً نحو المرشح المراجَع. |
| `cancel` | يوقف الإرسال اللاحق ويحفظ الأدلة المتحقّقة للاستئناف. |

رمز الخروج 0 يعني نجاح الإجراء، و2 يعني الحظر أو الرفض مع حقل `error` في التقرير.

`--image` يختار صورة التنفيذ (الافتراضي `python:3.14-slim`)، و`--workers` يتجاوز قيمة الملف،
و`--reason` يسجّل سبب الإلغاء. في مشاريع المراجعة الموثّقة تأتي بيانات الاعتماد من
`CREWLOOM_REVIEWER_TOKEN` أو من `--reviewer-token-stdin`، ولا تأتي أبداً من سطر الأوامر.

## ما تفعله كل مهمة فعلياً

1. يُنشأ `.crewloom/worktrees/<batch>/<task>` على الفرع `crewloom/<batch>/<task>` عند الأساس الثابت،
   مع ربط checkout محلي جديد لهوية المشروع المحمولة نفسها.
2. تُدمج الالتزامات المتحقّقة للأسلاف في شجرة العمل أولاً وبترتيب الاعتماد، لتقرأ المهمة التابعة
   ملفات أسلافها لا الأساس غير المعدّل.
3. يعمل الـ workflow الحقيقي للمهمة، بنفس حد العزل والمدخلات والمخرجات المعلنة وسجل المحاولات
   وميزانية الفشل المعتادة.
4. تُلتزَم المخرجات المعلنة المتحقّقة فقط. إن احتوى الفهرس على أي شيء آخر يُرفض الالتزام. لا
   تُجمَع أبداً الملفات المولّدة مثل `AGENTS.md` أو تعديلات `.gitignore` أو ذاكرة الأدوار أو ملفات
   المستخدم أو `.crewloom`، وتبقى خطّافات Git فعّالة؛ فشل الخطّاف يترك الشجرة والمخرج للفحص
   ويبقي الدفعة قابلة للاستئناف.
5. تصبح المهمة `verified` فقط مع تشغيل مُدار مكتمل، وبصمات إدخال وإخراج ومعايير غير متغيّرة،
   ومحاولة منفّذ ناجحة لكل خطوة أمر، ورابط checkout محلي مختلف.

الحالة في `.crewloom/coordinators/<batch>/state.json` مع سجل أحداث محدود الحجم مخصّص للمالك وحده
بجانبه. السجلّات مخصّصة للمالك تُستبدل ذرّياً ومحدودة بحجم، ويتوقف السجل عن الإضافة بدل أن ينمو بلا
حدّ. يطبع `status` مسارات أشجار العمل والفروع والالتزامات وملفات الأدلة والحدود المسجّلة بالضبط.

## الفشل والحظر والاستئناف والإلغاء

- المهمة الفاشلة أو المحظورة تحظر كل مهمة تعتمد عليها، مع تسجيل معرّفات الحاجزين. لا يوجد قبول جزئي.
- الاستئناف يعيد إثبات كل مهمة متحقّقة — سجل المنفّذ وبصمات المخرجات ورأس شجرة العمل وخطة الـ
  workflow والمعايير وملف الوصف نفسه — قبل تخطّيها. لا تُنفَّذ مهمة متحقّقة مرتين؛ تغيير السبب شرط
  لإعادة تشغيل مهمة فاشلة.
- ملكية الدفعة بقفل استشاري تحتفظ به النواة. يُرفض منسّق ثانٍ، ويُعدّ المتحكّم المتوقّف قد انتهى لأن النواة
  هي حرّرت القفل. لا تُنتزع الملكية أبداً من PID مسجّل، فلا يُعامَل PID غير معروف أو مُعاد
  الاستخدام كأنه ميت.
- `cancel` أثناء عمل متحكّم حي يكتب طلباً دائماً: يتوقف الإرسال، ويُفرَغ العمل المُدار الجاري،
  ويُحرَّر الجذر، وتُسجَّل المهام المتحقّقة. النتائج المتحقّقة تُحفظ، ويعود `run` للاستئناف دون
  محاولات منفّذ جديدة. لا تُدمج دفعة ملغاة ولا تُنشر دون `run` ثم `prepare` ثم `review` جديدة.
- المنسّق لا ينهي إلا ما يملكه. الحاوية أو الأمر الذي تجاوز عمر متحكّمه لا يوقفه أي قفل تملكه هذه
  الأدوات.

## الدمج والنشر بعد المراجعة

`prepare` ينشئ `.crewloom/worktrees/<batch>/integration` عند الأساس المتوقع، ويدمج التزامات المهام
المتحقّقة مرة واحدة بترتيب الاعتماد مع كسر التعادل بمعرّف المهمة. التزامات المهام تحتوي على المخرجات
المعلنة فقط، فيحمل الدمج فروق المخرجات. يُسجَّل أي تعارض بمساراته، وتُحفظ كل الفروع وأشجار العمل
والفهارس وملفات الأدلة، ولا يُعاد ضبط شيء ولا يُفرض ولا يُنظَّف. بعدها يعمل القبول المدمج داخل شجرة
العمل نفسها عبر المنفّذ المعزول نفسه، وتُلتزَم مخرجات القبول عمداً كجزء من المرشح.

يحتاج `review` الأساس ورأس المرشح وبصمة الفرق بالضبط، ويسجّل إما معرّف مراجعة معلَن أو إثباتاً موقّعاً
ببيانات اعتماد. في الوضع الموثّق سجلّ المراجعين في المشروع هو جهة الإصدار: تُفحص التوقيع ونسخة
الإصدار والإلغاء. في وضع المعرّف المعلن لا يوجد توقيع، والتقرير يصرّح بذلك. يغطي الإثبات مجموعة
المخرجات المراجَعة ومعايير القبول، ولا يمكن إعادة تشغيل قرار مستهلك.

يعيد `publish` التحقق قبل أول بايت: ملف الوصف، هوية المشروع ورابط الـ checkout، كل التزام مهمة،
بصمات المخرجات، المعايير، هوية شجرة العمل، رأس الدمج، بصمة الفرق المعاد حسابها، الإثبات وإلغاؤه،
`HEAD` الجذري، نظافة الشجرة المتعقَّبة، وتصادمات الملفات غير المتعقَّبة المقارنة بالمسار القانوني.
عندئذ فقط ينفّذ تقدّماً سريعاً واحداً بـ `--ff-only` تحت قفل المشروع، ويسجّل nonce المستهلَك،
ويحرّر حجز الجذر. ليس هذا إعادة ضبط أو اختياراً اعتباطياً أو إعادة كتابة تاريخ أو دفعاً أو دمجاً على
GitHub، ولا تُحذف الملفات غير المتعقَّبة أبداً.

## ملكية جذر المشروع

تأخذ الدفعة الجذر طوال عمرها بالحجز نفسه الذي يكتبه الـ workflow المُدار، فيرفض `workflow run`
و`crewloom project enter` الجذر أثناء الحجز، والعكس صحيح. يُحفظ قفل المشروع حول تغييرات الحالة
وعمليات Git القصيرة فقط، لا حول الدفعة المتوازية كاملة، لأن كل شجرة عمل تأخذ قفل جذرها الخاص أثناء
تشغيلها.

## الحدود، بصدق

- دفعة واحدة لكل جذر في الوقت نفسه، بحد أقصى 4 عمّال و32 مهمة، جميعها على أساس واحد ثابت.
- تُنفَّذ خطوات `command` و`model` عبر مشغّل workflow داخل شجرة كل مهمة. خطوة `task` اليدوية تحتاج مراجعة خارج الدفعة.
- تشغيل Codex أو Claude أو OpenCode يحتاج القرارين معًا: `native_host_cli: true` في المهمة و`--allow-host-cli` في التشغيل؛ الرفض يحدث قبل استدعاء المزوّد. حدود الطلبات تخص سجل كل شجرة عمل، وليست سقفًا ماليًا للحساب أو للمشروع كله.
- لا تُلتزَم ملفات ضبط المشروع — `.gitignore` و`AGENTS.md` و`CLAUDE.md` و`crewloom.project.json` —
  أبداً كمخرجات مهمة.
- تحتاج ملكية الدفعة قفلاً استشارياً على POSIX؛ ودون ذلك يرفض المنسّق بدل التخمين. يبقى للتقدّم
  السريع لـ Git حدود الذرّية الموثّقة في Git نفسه، فإن انقطاع العملية بين تسجيل النشر والتقرير النهائي
  يترك الالتزام المرشّح موجوداً للفحص.
- المراجعة بمعرّف معلَن تسمّي مراجعاً. وبيانات الاعتماد تثبت حيازة سرّ م principal مسجَّل. ولا
  يثبت أيٌّ منهما أن إنساناً متبايناً راجع العمل، ولا ninguno حاجز نظام تشغيل ضد مالك المشروع.
- التنسيق المُدار ليس حداً لأدوات المضيف العشوائية؛ من يكتب خارج هذه الضوابط يبقى خارجها.

## الأدلة

يسجّل [COORDINATOR_ACCEPTANCE.json](COORDINATOR_ACCEPTANCE.json) دفعة حقيقية من ثلاث مهام على
`python:3.14-slim`: عاملان متداخلان، مهمة تابعة تقرأ أسلافها المدمجين، قبول مدمج على الشجرة
المدمجة، قرار مراجعة، وتقدّم سريع للجذر نحو المرشح. وتوفّر سكربتات الاختبار المخرجات،
إذاً يثبت ذلك التنسيق والعزل والدمج والنشر لا توليد شيفرة بالنموذج.
