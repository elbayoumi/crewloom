# Practical agency acceptance

Crewloom is not considered delivery-ready solely because its repository checks or synthetic understanding pilot pass. The next acceptance run must exercise a complete, inspectable project without private client data.

## Delivery requirements

1. Bind an independent canonical project and task identity. Run a second project concurrently with distinct source markers; every output, memory record and event must retain the correct project and task. Resolve and reject cross-project writes.
2. Discovery produces a source-linked brief, explicit constraints and observable acceptance. Quotes, interpretations and unknowns remain distinct. Ask only questions needed for the current action: classifying a publication request does not require deployment credentials.
3. Architecture and implementation produce a runnable multi-file feature from the inspected project. Preserve existing behavior and record real commands, results and failure evidence.
4. A specialist QA role independently verifies functional behavior, invalid inputs, project isolation and the user-selected Arabic/English requirements. Reviewer prose alone is not executable verification. For localized product surfaces, run equivalent Arabic and English acceptance, including RTL/LTR, switching and applicable persistence/error states; see [language support](LANGUAGES.md).
5. Delivery produces reviewed artifacts and an evidence packet linking requirements to actual files and checks. Publish only explicitly selected public files; retain local conversation, role memory and raw transport privately.
6. A correction after the first delivery updates the relevant scoped contract and changes only the selected task. Demonstrate interruption/resumption and inspect the final artifacts rather than relying on a successful exit code.

## Evidence required before claiming completion

Retain the original brief and corrections, frozen inputs/model settings, every generation attempt, independent verification output, artifact hashes, publication selection and project-scoped task records. Report unavailable/failed attempts. Verify actual CLI and dashboard behavior where used. Distinguish synthetic cases, fixture execution and real model delivery; neither a mocked host nor an always-passing verifier proves delivery.

The completed nine-scenario understanding pilot is supporting evidence only: selected context passed 17/18 responses versus 14/18 raw-history responses on one run per condition, with requested gpt-5.5 and unknown reported model identity. It does not prove statistical significance, general understanding, all specialist roles or business outcomes. The later operational acceptance below records its own scope and results.

## 2026-10-15 operational acceptance

[The machine-readable record](../examples/evaluation/agency-acceptance-20261015.json) preserves the requested model trials and the failed/corrected phases. Two independent projects ran concurrently. The primary four-module application was delivered only after independent review added raw-rate edge cases: 70 application cases and 16 helper tests passed in Docker. Credential-reviewed publication fast-forwarded the exact candidate; interruption/resumption preserved verified generation counts. A staged Arabic output correction after delivery completed from executor evidence. Foreign project destinations and context were refused.

Source statements remain distinct from operator-selected scope and correction scenarios. Native prompt text is still host-provided input; this run is not proof of every host callback or every specialist role. All 42 guides validate structurally; live evidence is scoped to software, QA, context, MCP and selected machine operations. Other domains require representative inputs and acceptance before making performance claims.
