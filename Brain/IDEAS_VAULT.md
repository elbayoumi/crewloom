### 2026-10-06 — Proposed tool contracts and reusable cores
Owner discussion proposes a consistent standard for Crewloom tools, clean code and reuse. **Owner-confirmed scope: Crewloom toolkit tools only; application code and consumer-project scripts are outside this change.** Current `documentation/TOOLS.json` contains18 entries with id/skill/path/description/example_args/dependencies/effect; `crewloom.run` dispatches registered Python scripts and validates known path flags. It does not provide complete typed input/output contracts or universally enforce declared effects. This is a proposal, not a new runtime claim or approved migration.

Extend the existing catalog rather than build a competing registry. A versioned tool contract should describe purpose/owner, typed inputs and outputs, callable or executable entrypoint, dependencies, effects, required capabilities, timeout/output limits, retry/idempotency behavior and meaningful verification evidence. Describe payload shapes with a bounded supported schema dialect; do not claim arbitrary JSON Schema validation without a compatible validator. Keep source-relative portable identifiers distinct from the selected canonical project/task binding. Catalog discovery reads metadata without importing/executing arbitrary project code.

Separate reusable toolkit logic from filesystem/network/process adapters and thin CLI/UI/agent interfaces. Toolkit internal functions and tests require appropriate quality/contracts but do not all become public AI tools. Private verification fixtures remain attributable inside the selected ignored state; operational toolkit tools need reviewed promotion without project facts, credentials or automatic cross-project learning. This proposal does not rewrite consumer scripts or impose a new framework on application repositories.

A controller validates selected contracts and current permissions before managed execution; read-only/write/network declarations alone do not confine a direct host subprocess. Reuse the existing broker/container boundaries where their tested coverage applies. CLI arguments are arrays; machine results and diagnostics have separate channels. Preserve existing exit-code semantics through explicit adapter/version transitions. Persist operation identity and receipts; retry only according to verified operation semantics.

The agent should search reusable toolkit assets before creation, reuse a compatible tool, extend bounded existing behavior when appropriate and compose tools through validated outputs. Avoid a generic multi-purpose script or mandatory framework/classes for small functions. A newly generated toolkit tool starts as draft work, not an automatically trusted installed tool. Proposed quality gates cover contract validity, unregistered operational entrypoints, dependencies, imports without side effects, known path escapes and meaningful negative/positive acceptance; lint and formatting do not establish domain correctness.

Generate human catalog/docs views from one machine contract source while preserving CODE_REGISTRY discoverability, ownership and existing contracts. Lazy discovery exposes short tool descriptions first and loads only a selected schema/implementation when needed. Measure retrieval/provider overhead and accepted-task quality before asserting token savings. Start with a few existing read-only tools and one controlled writer, preserve legacy wrappers/frozen acceptance and compare cold/warm overhead. If implementation is authorized, fit it into existing W03/W08/W12; it does not create a second active plan or displace open W01 privacy boundaries.
