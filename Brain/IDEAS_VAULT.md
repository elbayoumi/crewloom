# Ideas

### 2026-10-21 — Separate specialist evidence from runtime bookkeeping
Use independent project-role reviews to seek failures that a passing suite misses, then reproduce them with targeted tests and actual execution. Record runtime provenance and exact evidence scope; role labels and preview exit codes do not establish SDK or model execution.

### 2026-10-21 — Make integration mode explicit
Expose synchronous and awaited framework entry points separately instead of returning ambiguous dual-mode values. Test real consumer calls and populated installed environments; keep framework versions pinned in acceptance without making them core runtime dependencies.

### 2026-10-20 — Validate contracts at the external consumer
Test the real pinned framework call path, installed library use in a populated consumer project, OS-level output and actual network connection selection. These boundaries cannot be established by helper-level mocks or import-only artifact checks.

### 2026-10-20 — Preserve state in the execution boundary
A live isolated interpreter preserves functions and imports without re-executing prior side effects or deserializing host state. Make ownership, policy reuse, teardown, lost-state errors and persistent CLI cleanup explicit, and keep the simpler one-shot path for stateless execution.

### 2026-10-20 — Test capability transitions and observable side effects
Pair outside-checkout adapter imports with actual built archives, default/empty/explicit write policies with real containers, optional-parser installation with a warm cache, and sequential session execution with persistent-file assertions. Component mocks and isolated cold-start checks cannot establish these contracts.

### 2026-10-15 — Construct async authority inside its execution loop
Keep synchronous scope validation independent from event-loop allocation. Create async serialization primitives only during actual asynchronous use and bind the controller to that loop. Test real contention and reject foreign-loop reuse rather than relying on newer runtimes' lazy behavior.

### 2026-10-15 — Make skipped acceptance visible
Optional core coverage and explicit integration acceptance need separate outcomes. When an operator enables an integration, unavailable prerequisites should produce a failed run with a setup diagnosis. Keep screenshot/provider/native opt-ins individually labelled so a passing job cannot imply acceptance of every capability.

Evaluate repeatable role tasks in both Arabic and English across target agent hosts. Keep provider-specific evidence separate from structural checks and local tool tests. Add optional components only with clean setup instructions and meaningful behavioral tests.


### Role evaluations
Build reproducible, synthetic end-to-end role tasks with independently reviewed outputs, extending structural checks without claiming unmeasured performance.

### 2026-10-01 — Project path isolation
Project-scoped host permissions can extend the entry-point path guards to arbitrary tool execution.

### 2026-10-01 — Role installation memory isolation
Keep reusable role upgrades separate from project state migrations and validate each migration against its selected project.

### 2026-10-01 — Executable software workflows
Extend the label-free grader with independently frozen acceptance suites for additional software features and models. Keep model-treatment mapping outside the grader and record cost alongside correctness.

### 2026-10-01 — Harder provider acceptance
Freeze private multi-file feature contracts, record exact model identity and cost, and use a coordinator independent of the producer. A full-acceptance tie on a public pure function cannot establish the benefit of specialist procedures.

### 2026-10-01 — Named maintenance activation
Use a stable bilingual workflow name to invoke verified in-place repairs without changing role IDs or implying an autonomous runtime.

### 2026-10-02 — Enforced runtime follow-up
Add provider-backed integration evidence after local credentials are configured, account-level spend controls and transactional multi-file publication. Keep unmanaged host permissions explicit.

### 2026-10-02 — Context efficiency
- Evaluate selected-memory correctness on frozen tasks, record actual provider token/cached-token usage, and add indexed retrieval only if lexical selection misses useful lessons.

### 2026-10-02 — Repository navigation
- Add optional Tree-sitter adapters and precise import graphs only after measuring missed symbols and retrieval quality; retain dependency-free core and explicit provider metadata scope.

### 2026-10-02 — Automatic context implementation plan
- Use task-boundary refresh and project/checkout/task identities before adding filesystem watchers or semantic dependencies. Pilot observable token/correctness effects before all-project rollout.

### 2026-10-02 — Automatic context implementation
- The initial draft crossover (superseded: selected context 62.6% of full at 24 files, 0.92% at 604) suggests publishing the crossover point per project instead of a universal percentage, and keeping `source_roots` as the first lever for very large repositories.
- Executor-gated lesson promotion is a reusable pattern for any local learning store: keep the promotion input a project-recorded artifact, never a prose claim, and re-check policy fingerprints before reuse.
- Off/observe/enforced plus an honest lifecycle label (`managed-runner`, `instruction-assisted`, `manual`) lets a host that cannot offer callbacks still adopt context without a false automation claim.

### 2026-10-02 — Bounded delegation handoff
- Preserve acceptance, failure counters, source state and verification references in a compact checkpoint; keep verbose execution history on disk. A fresh model session can reduce repeated context without erasing attempts or reducing task scope.

A future scheduler should preserve canonical root and active-workflow reservations instead of sharing a writable checkout between workers.

### 2026-10-03 — Keep savings tied to frozen tasks
Compare complete declared inputs and unchanged acceptance contracts across context modes before claiming billed-token or quality gains; current public byte measurements are navigation evidence only.

### 2026-10-04 — Validate automatic context as a complete chain
Verify callback delivery, explicit project/session/turn identity, fresh declared source, guarded edits and recorded executor acceptance separately. Installation or idle status cannot establish successful context use. Provider usage remains a measured, nullable field rather than an inferred saving from source bytes.

### 2026-10-04 — Aggregate request admission for concurrent worktrees
A future batch-level request counter should reserve remaining generation slots before dispatch, reconcile them against worker ledgers and preserve reservations across failures and resume. The current managed request ceiling applies to one checkout ledger; do not describe it as a provider-account or aggregate multi-checkout billing cap.

- Native adapter acceptance must include the actual launcher configuration shape and distinguish configuration readiness from observed context delivery. Offline callback tests cannot establish host parsing or production callback behavior.

### 2026-10-05 — Preserve native boundary evidence
Store a bounded, project-owned callback schema receipt alongside version and source fingerprints. Verify allowed edits, refused edits and post-edit refresh separately: a denial caused by a broken payload parser cannot establish a useful guard. Keep installation readiness, callback observation, actual model context use and executor acceptance as distinct claims.

### 2026-10-05 — Editable CLI exposure
Use a dedicated pipx environment for a globally discoverable development CLI; record its source checkout explicitly so a later worktree move is followed by a deliberate reinstall.

### 2026-10-05 — Dependency-closure maps
A map that always includes the bodies of every symbol the selected module imports could keep the token cut without the quality collapse seen in the first study; test it as a new preregistered arm, not a retrofit.

### 2026-10-09 — Separate monitoring from execution selection
A dashboard can monitor multiple registered roots without changing its writable project. Resolve mutations from server-side IDs and let existing locked lifecycle actions handle them; do not trust roots supplied by the browser.

### 2026-10-09 — Scope password-free access to the launch boundary
Choose local access on the server, rather than passing a hidden shared password into the browser. Keep remote hosting an explicit authenticated choice.

### 2026-10-10 — Scheduling, shared admission and measured activity
- Separate durable queue intent from project execution authority. Persist dispatch before calling providers, preserve interrupted jobs for explicit review/retry, and keep unknown spend conservative. Broaden evaluation only after host availability is demonstrated.

### 2026-10-11 — Evaluate understanding before automatic extraction
Compare the same model on frozen Arabic/English correction and ambiguous-request conversations, with and without source-linked context. Score wrong-project selection, invented preferences, missed corrections and unnecessary questions separately. Do not promote extracted preferences to facts merely because an LLM produced them.

### 2026-10-11 — Separate local customization from publication
Keep personal preferences as scoped private input data instead of editing distributed role guides. Future publication review can compare selected-file hashes and provenance, but must not convert a clean pattern scan into a claim that arbitrary content is public-safe.

### 2026-10-14 — Preserve identity across automation layers
- Carry tab/frame/document/request identity from discovery through execution and return transport. Keep manual activation separate from agent automation consent; test delayed replies, navigation and disabled state in the real transport. Project/task identity must survive the same boundary in a future MCP bridge.

### 2026-10-14 — Host capability separation
- Keep the task/context/artifact MCP boundary reusable across hosts; attach an independently authorized browser or native desktop provider rather than expanding candidate import into arbitrary host execution. A host-capability matrix should record verified calls, permissions, application targets and unresolved scope.

- 2026-10-14 | Keep native acceptance scoped to an account-free synthetic target before expanding actions. Independent mock refusal, human-approved driver capability, actual Accessibility state and a re-observed application postcondition are separate evidence.

- 2026-10-15 | Keep live native acceptance opt-in and preserve a unique receipt for every attempt. Separate source and installed-runtime receipts; test foreign PID refusal and stale handles alongside visible state transitions.

- 2026-10-15 | Use real generation failures to refine explicit runtime contracts without altering the frozen verifier. Freeze task-source context at the worktree boundary as well as inside model prompts. Report quality per attempted role and task, with failed and blocked runs retained.

- 2026-10-16 | Close an operational acceptance with a published code candidate, a post-delivery correction completed from executor evidence, a per-role coverage inventory and retained failed phases. Unknown backend identity/cost and untested domains remain explicit fields, rather than blocking delivery of verified toolkit capabilities.

- 2026-10-17 | Use equivalent language/direction/error acceptance for every localized change. Keep application labels and third-party diagnostics intact; a translation count or role-guide translation cannot demonstrate bilingual runtime quality.
