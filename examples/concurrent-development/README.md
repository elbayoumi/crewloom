# Concurrent development example: ledgerline

A complete, runnable example of concurrent AI development under Crewloom. Three tasks in a
dependency graph, each task generated by a real `model` step inside its own Git worktree,
each generated file verified by a real container command, one combined acceptance, and one
reviewed fast-forward into the checked-out tree. The application is small but real: it
computes an invoice summary and an execution plan, in English or Arabic, from a JSON document.

Everything here is one command away. Nothing in this directory talks to a provider by itself:
the `crewloom coordinator run` command does, and only because you named one host and one
exact model.

## What the example ships

| Path | What it is |
| --- | --- |
| `setup_project.py` | Creates a fresh bound project: copies the assets, substitutes the manifest and workflows, installs two roles, commits, registers a reviewer, and finishes with the coordinator's own read-only preflight. |
| `project/` | The project that gets copied: contracts, workflows, manifest, criteria, input documents, frozen helper tests and the acceptance commands. |
| `fixtures/generated/` | The module bytes the offline acceptance run uses as its stand-in provider output. They are real working code, and the acceptance commands execute them. |

The project layout after setup:

```
crewloom.project.json     portable identity, observe policy, verified review
criteria.md               the acceptance criterion, tracked at the base commit
contracts/                the explicit contract each generation step is given
  invoicing.md  planning.md  report.md
data/                     frozen input documents (ledger_en.json, ledger_ar.json)
src/money.py              reused verbatim from the context-study example
src/scheduling_support.py reused verbatim from the context-study example
src/{billing,planning,report,app}.py   what the three tasks generate
tests/                    frozen fixture tests for the two reused helpers
tools/                    the five acceptance commands
workflows/                four declared workflows
coordinator.json          the batch manifest
.crewloom/                runtime state and the issued credential; never tracked
```

## The task graph

```
billing   (independent) ─┐
                        ├─> report (dependent) ─> integration ─> review ─> publish
planning  (independent) ─┘
```

| Task | Generates | Verified by |
| --- | --- | --- |
| `billing` | `src/billing.py` | `tools/check_billing.py` in a container: 21 cases |
| `planning` | `src/planning.py` | `tools/check_planning.py` in a container: 20 cases |
| `report` | `src/report.py`, `src/app.py` | `tools/check_report.py` in a container: 14 cases |
| integration | — | `tools/check_combined.py` and `tools/run_helper_tests.py`: 13 cases and the frozen helper tests |

`report` is declared with `src/billing.py` and `src/planning.py` as inputs of its generation
step, so the ancestor modules are merged into its worktree and are part of the prompt it
actually receives.

## 1. Setup

Pick a directory that is not already a Git work tree, not inside another project, and not a
symlinked alias of one. `/tmp` is not canonical on macOS; use `/private/tmp`.

```bash
python3 examples/concurrent-development/setup_project.py \
  --destination /private/tmp/ledgerline \
  --project-id ledgerline-demo \
  --model-host openai \
  --model gpt-4.1
```

The setup command refuses, before writing anything: an existing destination, a destination
whose parent is a symlink, a destination inside the Crewloom installation, inside another
bound project, inside an installed role tree or inside another Git work tree, a missing or
blank exact model, an unknown host, an installed-CLI host without `--native-host-cli`, a
tool-free host with it, and a missing provider credential. It never picks a model for you and
never falls back to another host.

For an installed CLI host such as `opencode` or `codex`, add `--native-host-cli`. That
decision is written into the committed manifest, and the run still needs `--allow-host-cli`.

Setup prints a JSON report containing the base commit, the bound checkout ID, the two
installed roles, the accepted preflight and the path of the issued reviewer credential.

## 2. Validate, run, status

```bash
PROJECT=/private/tmp/ledgerline
ID=ledgerline-demo

crewloom coordinator validate --project $PROJECT --project-id $ID --manifest coordinator.json
crewloom coordinator run      --project $PROJECT --project-id $ID --manifest coordinator.json
crewloom coordinator status   --project $PROJECT --project-id $ID --manifest coordinator.json
```

`run` needs the provider credential in the environment and nothing else. For an installed CLI
host, add `--allow-host-cli`. Two tasks run concurrently; the third starts only after both
are verified.

`status` prints the recorded batch: exact worktree paths, branches, task commits, image IDs,
the per-task evidence ledger and the recorded limits.

## 3. Prepare, inspect, review, publish

```bash
crewloom coordinator prepare --project $PROJECT --project-id $ID --manifest coordinator.json
```

`prepare` merges the verified task commits into the integration worktree and runs the
combined acceptance there. Read the actual diff before you authorize anything:

```bash
git -C $PROJECT diff --stat $BASE..$CANDIDATE       # from the prepare report
git -C $PROJECT diff $BASE..$CANDIDATE              # the exact bytes you are reviewing
cat $PROJECT/.crewloom/worktrees/ledgerline-batch/integration/artifacts/combined_acceptance.json
```

Then deliver the reviewer credential through the environment or standard input, never as an
argument, and record one decision over the exact base, candidate head and diff digest:

```bash
export CREWLOOM_REVIEWER_TOKEN="$(cat $PROJECT/.crewloom/reviewer-token-example-reviewer)"

crewloom coordinator review  --project $PROJECT --project-id $ID --manifest coordinator.json \
  --expected-base $BASE --candidate-head $CANDIDATE --diff-sha256 $DIFF
crewloom coordinator publish --project $PROJECT --project-id $ID --manifest coordinator.json \
  --expected-base $BASE --candidate-head $CANDIDATE --diff-sha256 $DIFF
```

Without a reviewed decision, `publish` refuses. `publish` revalidates everything and then
moves the checked-out tree by one `--ff-only` fast-forward.

## 4. Use the published application

```bash
cd $PROJECT
python3 src/app.py --data data/ledger_en.json --out artifacts/report.json
python3 src/app.py --data data/ledger_ar.json --out artifacts/report-ar.json --language ar
```

The Arabic report of the frozen sample contains:

```json
"by_currency": { "SAR": { "net": "302.00", "tax": "45.01", "gross": "347.01", "per_line_tax": "45.00" } }
```

Two lines of tax `0.005` each: the group total rounds once and is `45.01`, while rounding
each line first gives `45.00`. That difference is the reason the report carries both numbers.

A refused document is reported as one JSON object on standard error with exit status 2, and
no output file is written:

```bash
python3 src/app.py --data missing.json --out artifacts/x.json ; echo "exit $?"
```

## Failure, resume and cancellation

| Situation | What happens | What to do |
| --- | --- | --- |
| A task's acceptance fails | The task is `failed`, every task depending on it is `blocked`, and nothing is integrated or published. The root does not move. The unaccepted generated file stays in the worktree, uncommitted. | Change the cause, then run again. |
| A generation or a command failed twice unchanged | The executor refuses the third identical attempt rather than looping. | Change the input or the contract, then use a new batch ID. |
| You interrupted the controller | The kernel released the batch lock, so the next controller is not blocked by a dead one. | `crewloom coordinator run` again. Verified tasks are re-proved and never re-run. |
| You want to stop | `crewloom coordinator cancel --project $PROJECT --project-id $ID --manifest coordinator.json` | A live controller stops dispatching, drains, releases the root and keeps verified work. A cancelled batch needs a fresh `run` and `prepare` before it can be published. |
| The manifest, criteria, base or a worktree identity changed | Refused, by name, before any write. | Use a new batch ID for changed work. |

Every recorded fact is in `.crewloom/coordinators/ledgerline-batch/state.json`, with a
bounded event log beside it and the retained worktrees under
`.crewloom/worktrees/ledgerline-batch/`.

## Offline acceptance, with no provider

```bash
CREWLOOM_DOCKER_TESTS=1 python3 -m unittest discover -s scripts -p test_development_example.py
```

Without the variable the Docker cases are skipped and the rest still run the real
application, the real setup command and the real coordinator preflight. With it, the real
coordinator runs this project over real Docker containers. Only the generation transport is
replaced: a stand-in provider returns the shipped bytes in `fixtures/generated/` and records
every request it was asked to make. That proves the coordination and the verification, not
any model's quality, latency or cost.

## What this example does not show

- No live provider call is included, and no usage or cost figure is claimed.
- A credential proves possession of a registered principal's secret. It does not prove that a
  distinct human read the diff, and the acceptance evidence does not prove the generated code
  is good beyond the assertions the commands ran.
- An installed CLI host is a native host exception, not an OS sandbox.
- Managed coordination does not stop a host tool that writes outside these guards.
