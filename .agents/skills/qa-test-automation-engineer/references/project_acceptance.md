# عقد قبول المنتج والتخزين والهوية بين التيمات

أُضيف استجابة لطلب المالك إصلاح التيمات أولاً بعد عطل الحفظ وتضارب ألوان عقار سيف. هذا عقد لتسليم مشاريع لاحقة، ولا يعني أن مشروع عقار سيف أُصلح.

## 1. مهندس الستاك → المنفذ → QA
- حدّد لكل عملية هل المطلوب تخزين دائم، أم مجرد تحقق/معاينة. سجل الكيان ومكان تخزينه، مسار الكتابة والقراءة، ملفات migrations، ومعالجة فشل الاتصال. لا تُترك هذه اختيارات ضمنية للقالب.
- اختيار SQL مباشر أو ORM قرار موثق حسب الحاجة. وجود schema.sql أو حزمة ORM أو mock لا يثبت اتصالاً أو حفظاً. لا تفرض ORM على كل مشروع، ولا تسمِّ عدم وجود طبقة بيانات اختياراً معمارياً مكتملاً.
- أي مسار يعد المستخدم بحفظ/إرسال نهائي لا يرجع نجاحاً عند غياب إعداد التخزين أو فشله. webhook اختياري وذاكرة عملية وملف محلي على استضافة مؤقتة ليست دليلاً كافياً على دوام البيانات.
- QA يكتب integration test ضد مخزن اختبار حقيقي: كتابة بعلامة فريدة، قراءة عبر اتصال مستقل، استمرار السجل بعد إعادة تشغيل التطبيق، وفشل صريح عند تعطيل المخزن. يختبر الواجهة في النجاح والفشل؛ لا تستبدل هذه الأدلة بـ toHaveBeenCalledWith أو status 201.
- الاختبارات لا ترسل رسائل لأشخاص أو webhooks حقيقية؛ اعزل تكاملات الخارج ونظّف بيانات الاختبار. لا تُنسخ أسرار أو بيانات عميل في تقرير الأدلة.

## 2. فاحص الحفظ الموجود
الفحص الافتراضي للشفرة تشخيص استرشادي فقط؛ exit 1 يشير إلى عيب مشتبه، وexit 2 يعني أن الحفظ لم يُختبر. لا يوجد نجاح قبول من regex مهما ظهر اسم prisma/db أو استدعاء mock.


هذا الأمر يكتب فعلياً ثم يقرأ بعلامة مطابقة عبر طلب مستقل. exit 0 يثبت roundtrip واحد فقط، ويطبع أن restart_durability وstorage_outage غير مختبرين. لا يعفي من اختبارات إعادة التشغيل وتعطل المخزن ولا اختبار صلاحيات المستخدم. تنظيف السجل مسؤولية بيئة الاختبار.

## 3. الهوية → المصمم → مدقق الواجهة
- الهوية تحدد مسار tokens الخاص بالمشروع ومصدر اعتماده، ودور كل لون: خلفية، سطح، نص، إجراء أساسي، وحالات نجاح/خطأ. توكنز الوكالة تُستخدم لمنتج آخر فقط إذا كان يرث هويتها بقرار صريح.
- المصمم يستخدم هذه الأدوار في المكونات؛ لا يستعيد ألوان القالب ولا يغير ملف هوية الوكالة لمعالجة عميل. اللون المساعد لا يزاحم زر الإجراء، ولا يُملأ كل سطح بلون accent.
- المدقق يشغّل check_palette_drift.py مع --project-dir و--tokens لمسار JSON المعتمد. exit 1 انحراف مكتشف؛ exit 2 نقص أو عدم دعم للفحص؛ exit 0 نجاح للفحص النصي المدعوم فقط. غياب التوكنز لا يساوي نجاحاً، وعدم استخدام كل توكن ليس خطأ.
- الأداة تقارن لوحة Tailwind النصية بالتوكنز المختارة، وتكشف سلاسل الألوان الافتراضية وhex في CSS/JSX. الثيم المحسوب أو المستورد، الألوان الوظيفية والأنماط المولدة تحتاج فحص المتصفح أو توسيع الفاحص؛ لا تدّع تغطيتها آلياً.
- يلزم screenshot ومراجعة computed styles وcontrast في المقاسات الثلاثة. مطابقة التوكنز وحدها لا تثبت أن الألوان مناسبة أو أن التباين مقروء. عند رفض المالك الاتجاه، تُراجع الهوية قبل الاستمرار في التزيين.

## 4. مدير التسليم
لا يجمع «build ناجح» و«شكل جميل» كقبول كامل. تقرير التسليم يربط كل متطلب بمخرج واختبار ومجال تحقق (محلي/تكامل/إنتاج). يظل غير المختبر واضحاً؛ تجربة لا تحفظ البيانات تُسمى تجربة صراحة ولا تعرض رسالة حفظ نهائي.

التسلسل: قرار التخزين والهوية → تنفيذ → اختبار حفظ حقيقي وفحص ألوان → مراجعة بصرية → تدقيق نهائي مرة واحدة. الملاحظات تعود كعيوب محددة، لا تعيد الدورة كاملة. صاحب العيب ومسار إصلاحه وحد المحاولات يتبع سجل skill-performance-auditor.

## 5. التفعيل الآلي وحدوده
اختبارات أداتي الحماية مضافة إلى run_skill_regressions.py الذي تستدعيه بوابة commit وCI الحالية. هذا يمنع انحدار الأداتين عند مرور التغييرات بالبوابات. فحص التطبيق الحقيقي يحتاج تشغيل الأمرين واختبارات تكامل المشروع ضمن CI الخاص به؛ لا يوجد ادعاء بأن بوابة المستودع تختبر كل قواعد بيانات العملاء تلقائياً.

## 6. صفحة أولى ومراجعة مستقلة قبل التعميم

مدير التسليم يسجل المستخدم، هدف الصفحة، رحلتها الأساسية، المحتوى الفعلي، الهوية والمراجع مع سبب الاختيار. المصمم ينفذ صفحة ممثلة للمنتج أولاً؛ لا يعمم الاتجاه على بقية الصفحات قبل مراجعة النموذج. في مشروع قائم اختر صفحة متضررة واحتفظ بدليل قبل/بعد. الاسم الغائب يتبع عقد التسمية الموجود، لا يعطل العمل التقني المستقل.

المصمم مسؤول عن التنفيذ والمبررات، ومدقق الواجهة يراجع الشكل والاستعمال والتجاوب والكيبورد والوصول، وQA يختبر الرحلة وحالات الخطأ. المراجع شخص أو جلسة مراجعة منفصلة عن المنفذ، مع نتيجة وأدلة يمكن تتبعها؛ تغيير اسم الدور في التقرير لا يصنع استقلالاً. عند غياب مراجع مستقل يظل القبول غير متحقق. مدير التسليم يجمع النتائج، ولا يمنح نجاحاً من build أو اختبارات الأدوات.

## 7. ملف تسليم قابل للفحص

احفظ delivery-packet.json داخل مجلد أدلة المشروع وشغّل:

```bash
python3 .agents/skills/qa-test-automation-engineer/scripts/check_delivery_packet.py PATH/TO/delivery-packet.json --expected-revision CURRENT_SNAPSHOT
```

العقد schema_version=2: كائن JSON فيه project وrevision (commit أو معرف snapshot ثابت للنسخة المختبرة) وimplementer، ومصفوفتا checks وdefects. CURRENT_SNAPSHOT يؤخذ من المشروع الحالي مستقلاً عن الحزمة؛ لا تنسخه من حزمة قديمة. إذا كان هناك تعديل غير committed فلا يكفي HEAD: استخدم snapshot ثابتاً يضم التعديلات المختبرة. لا تنقل أدلة نسخة سابقة عند تغيير ما تختبره؛ أعد البنود المتأثرة فقط واربط النتيجة الجديدة بالنسخة الحالية.

كل check له id وstatus (pass أو unverified أو fail) وreviewer وrevision وevidence (قائمة كائنات path وsha256 لملفات محلية غير فارغة داخل مجلد الأدلة). البنود المطلوبة: brief، pilot، technical، visual، responsive، keyboard، accessibility، journey، error_states. في `technical` أضف `review_scope` يشمل build وbrowser وresponsive وaccessibility؛ المقصود مراجعة منفصلة بنتائج وأدلة فعلية، وليس خروج `check_ui_quality.py` الذي يظل unverified دائماً. أضف بنود التخزين والصلاحيات وغيرها بحسب متطلبات المشروع؛ القائمة الدنيا لا تعفي منها. responsive يتضمن لقطات فعلية لثلاثة مقاسات مع أبعادها، وباقي البنود سجلات خطوات ونتائج مرتبطة بالصفحات. المراجع يقرأ الأدلة ويثبت SHA-256 وقت المراجعة؛ لا تعِد توليد البصمة تلقائياً لمجرد إنجاح الحزمة بعد تغير الملف. الحزم القديمة ذات مسارات نصية فقط تُرفض حتى مراجعتها وتسجيل بصماتها، ولا تُرقّى إلى pass تلقائياً.

كل defect له id ثابت وseverity (critical/high/medium/low) وstatus (open/resolved) وowner وfailed_attempts عدد صحيح لا يقل عن صفر. عند الحل أضف verification_check يشير إلى check إعادة اختبار ناجح بأدلته. احفظ وصف العيب وخطوات تكراره والسبب الجذري في سجل المشروع، ولا تحذف العيوب القديمة أو تعيد تسميتها لتصفير المحاولات.

الملخص الديناميكي يعرض عدد العيوب المفتوحة حسب شدتها والمطلوب تصعيده؛ لا يختلق نسبة جودة. أي عيب مفتوح يمنع جاهزية الحزمة في هذا المسار، والحرج لا يمكن تعويضه بدرجة مرتفعة. بعد محاولتي إصلاح فاشلتين لنفس العيب، أوقف إعادة تكليفه بنفس الطريقة وسلّم السبب والأدلة والبدائل للمراجع؛ لا تعد الدورة كاملة ولا توقف بقية العمل المستقل. تسجيل المحاولات ومكافحة إعادة التصفير يستمران في سجل الحوادث الحالي، وليس في الملف القابل للتحرير وحده.

exit 0 = ready_for_review لسلامة تسجيل الحزمة وتطابق بصمات الملفات والنسخة المتوقعة فقط، exit 1 = blocked بنواقص أو عيوب، exit 2 = ملف غير قابل للفحص. product_approved يبقى false دائماً: مدير التسليم يعتمد المنتج فقط بعد مراجعة مستقلة فعلية للأدلة. البصمة تكشف تغير الملف مقابل البصمة المسجلة؛ لا تمنع شخصاً من تغيير الملف والبصمة معاً. الأداة لا تصادق على هوية المراجع أو صدق المحتوى أو أن النسخة التي أدخلها المشغّل هي الأحدث، ولا تفرض تاريخ المحاولات، ولا تشغّل اختبارات العميل تلقائياً. لا تُسمى بوابة نشر مثبتة دون ربطها بمشروع واختبار منع/سماح فعلي لذلك المسار.
